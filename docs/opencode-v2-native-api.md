# OpenCode 2.2.5 — native API v2 integration for PIE (PR #39)

## Root cause

The previously implemented OpenCode HTTP adapter targeted the **v1** routes
(`/session`, `/mcp`, `/session/status`), which respond with the
OpenCode web application's HTML on a **v2** server. The v2 protocol has
new route names, new response envelopes and new message schema. It is
not safe to fix this by merely prefixing legacy paths with `/api`.

Authoritative contract:
- https://opencode.ai/v2/docs/api
- https://opencode.ai/v2/docs/mcp-servers/
- https://opencode.ai/v2/docs/permissions/
- https://opencode.ai/v2/docs/cli/web

## Correct v2 setup

Config (generated by `tools/create_opencode_pie_config.py`):
- `mcp.servers.pie` instead of legacy `mcp.pie`
- `type:local`, `command: [python, -m, pie.interfaces.mcp_server, --root, PIE_ROOT]`
- `codemode:false` so tool calls remain directly observable
- `permissions` array, `shell` action instead of legacy `permission.bash`
- Deny shell/edit/web/subagent/external_directory/execute, deny all
  other `pie_*` tools and explicitly allow only the PIE status query
- `OPENCODE_PASSWORD` controls v2 Basic auth; do not depend on the
  removed/legacy `OPENCODE_SERVER_PASSWORD`
- CLI: `opencode serve --hostname 127.0.0.1 --port 4097`; no `--pure`

API:
- GET `/api/info`
- GET `/api/mcp` -> `{location, data: Mcp.Server[]}`
- POST `/api/session` -> `{data: Session.Info}`
- POST `/api/session/{id}/prompt` -> `{data: Session.Inbox.User}`
- GET `/api/session/active` -> `{data: object}`
- GET `/api/session/{id}/message` -> `{data: Message.Info[],cursor}`
- POST `/api/session/{id}/interrupt` instead of v1 `abort`

The v2 adapter, `src/pie/orchestrator/opencode_v2.py`, refuses to
declare success without all of these:
- Correct PIE root in the returned `/api/mcp` location
- A connected MCP server named `pie` in the v2 `data` array
- A session that reports the identical authorized PIE root
- A durable admitted user prompt
- An assistant message with a completed PIE status-tool record
  containing nonempty `state.content`
- An `idle` message with `outcome=succeeded` and a normal assistant
  `finish=stop`
- No transcript pagination or recorded disallowed tools
- Evidence including actual tool call ID and SHA-256 over the
  serialized tool output; raw output is not exposed publicly

The model's plain-text assertion "CURRENT" does **not** suffice.

## Isolated Windows test

The user's separate PR checkout and personal OpenCode should be
preserved. Use the updated `tools/start_opencode_pie_smoke.ps1` from
a clean checkout. It creates an ephemeral config and starts/stops only
a temporary server on localhost port 4097. The test probes the v2
server `/api/info`, `/api/mcp` and `/api/session/active`, and
returns `ready:true` only if the actual PIE root and MCP status match.
It does **not** run a model.

If the local server fails the preflight, DO NOT start a remote
execution. Inspect the precise local response and adjust only against
the installed binary's /api OpenAPI contract.

When preflight is green, validate `python -m unittest discover -s tests -v`
and `npx pyright`. Then, after independently rotating and revoking
the publicly disclosed gateway bearer, perform one locally authorized
read-only model run and inspect its session/evidence. Only after that
may one controlled remote task be used as end-to-end acceptance.
